llms.txt is a proposed text file at the root of a site that lists the pages you most want a model to read. It is a map. It is not a citation, and it is not a ranking.

Jeremy Howard published the proposal in September 2024, and the page was updated in August 2026.[^llmstxt] The idea is a short list of the pages you want a model to read, written so a person can audit it in one sitting. This site already publishes [its own file](/llms.txt). That is a fact about this site, not a traffic statistic. We publish it because we like a clean list of what we stand behind. We do not publish it because a counter moved.

Google's guide says Google does not use llms.txt for generative features in search.[^google] Keep that next to the proposal, or the proposal becomes a rumor. A file Google's generative features do not read cannot be the reason you show up in those features. The page still has to be indexed. The page still has to deserve the quote.

The [missing-file guide](https://check.abra-ca-dabra.app/check/guide/fix/missing-llms-txt) is the check if you want to know whether yours is absent, broken, or pointing at junk. The [answer-engine note](/blog/answer-engine-optimization) is what Google does require, which is ordinary SEO on a real page. The [GEO comparison](/blog/generative-engine-optimization-vs-seo) is the research on visibility and the click, if the file conversation has crowded that out.

## What a crawl of the files found

Ahrefs, in a study published in June 2026, looked at 137,210 domains in its web analytics that had traffic in May 2026.[^ahrefs] 28% published an llms.txt file, about 38,000 valid files. 97% of those files received zero requests in May. 96% of the requests that did arrive were bots. 19.5% of requests came from named AI tools, and 12% from audit or scanner tools. Sit with those shares before you schedule a project around the file. Most copies, in that study, were never asked for. When something did ask, it was usually a bot, and only a smaller slice of those requests were named AI tools.

We do not read this as "never publish one." We read it as "do not expect the file to be a doorway." A list nobody requests cannot fix a homepage that says nothing. A list that scanners request is not the same event as a model citing you in an answer a customer sees. The study is a count of requests against files, in one month, on domains that already had traffic. It is not a verdict on the proposal's taste. It is a verdict on how often the file was fetched.

Publish the file if you want a clean list of your pages. Do not expect Google to read it. Keep the pages indexed and worth citing either way.

The order of that advice is the order we use in the room. Pages first. Index first. A sentence a stranger can use. Then, if you still want the list, a short file that points at those pages and does not point at drafts, tag dumps, or anything you would be ashamed to have quoted. The file is a courtesy and a control. It is not the work.

## A worked example

Walk an independent bookshop. This is an example, not a study, and it has no score. Ade owns the shop. Cole runs the floor and the website on the same tired afternoons. People ask, online and at the desk, for a book for a grieving friend, for something a nine-year-old will actually finish, and whether tonight's reading is still happening. The site has a homepage, an events page that is sometimes stale, and a staff-picks page that is the best thing they have written all year.

Someone on a forum told Cole that models will not understand the shop without llms.txt. He generated a long file that linked every tag, every old event, and a draft page about a book club that never started. It looked thorough. It was a bad map. A model that actually fetched it would have been pointed at stale nights and a club that does not exist. A model that never fetched it, which is the common case in the Ahrefs count, would have changed nothing, and Cole would have spent the evening on the wrong artifact.

What we would want in the file, if they publish one, is short. The staff-picks page. The page that explains how to order a book they do not have on the shelf. The events page, only if Cole updates it when a reading is canceled. Not the tag archives. Not the draft. The proposal, since September 2024 and as updated in August 2026, is a list of the pages you want read. "Want" is the verb. It is not "everything the CMS can emit."

Roles make the file honest. Ade decides which pages represent the shop. If she would not hand that URL to a regular, it does not go in the list. Cole keeps the events page true, because a file that points at a lie is worse than no file. Whoever fetches or fails to fetch is not their audience. The person who needs a book this afternoon is. The staff-picks page has to stand alone if no model ever requests the map. That is the lesson in the request counts. 97% of the valid files in the study got zero requests in May 2026. A shop that only improved the file, and left the picks page mushy, improved the thing almost nobody asked for.

Google sits to the side of this scene on purpose. The guide says Google does not use llms.txt for generative features in search. Ade can publish a beautiful file and still be absent from those features if the picks page is thin, blocked, or impossible to snippet. The answer-engine work is the page. The file is optional housekeeping. We would tell Cole that directly, before he buys a plugin that regenerates the list every night from every URL it can see.

And the request mix matters when someone waves a log at you. 96% of the requests that did arrive, in that June 2026 study, were bots. 19.5% came from named AI tools. 12% came from audit or scanner tools. A hit in a log is not a customer. It is often a machine checking whether the file exists. Treat a scanner hit as a scanner hit. Do not report it to Ade as demand.

## How we'd run it

We would decide whether the list is worth keeping, and we would write it by hand the first time.

First, choose the pages you hope a stranger finds, with Ade in the room. Staff picks. Ordering a title you do not stock. Tonight's reading, if and only if it stays current. If you cannot name them without opening the CMS and scrolling, you are not ready to publish a map.

Second, make those pages good enough to cite with no file at all. Indexed. Clear opening lines. A sentence Cole would say at the desk. Google does not use the file for its generative features, so this step is the one that can affect that surface. The [answer-engine note](/blog/answer-engine-optimization) is the longer version of what "good enough" means. Do not skip it because a file feels more concrete.

Third, write a short llms.txt that points only at those pages, with a line of plain description a person can check. Link the live URL. If the events page is stale, leave it off until Cole fixes it. A short true list beats a long generated one. This site's own file is that kind of choice. It is not evidence that files bring visits.

Fourth, put the file at the root and then forget the fantasy. Ahrefs looked at 137,210 domains with traffic in May 2026 and found that 28% had a file, about 38,000 valid ones. 97% of those saw zero requests that month. If yours is among the quiet majority, the shop does not get to feel broken. The pages are still the product.

Fifth, if you do watch logs, separate machines from people. 96% of requests in the study were bots. Named AI tools were 19.5% of requests. Audit and scanner tools were 12%. A spike from a scanner is not a crowd of readers. Do not rewrite the shop around it.

Sixth, revisit the list when the shop changes, not on a timer. A new picks page, a retired book club, a reading series that ended. Ade removes the dead link the same week. A file that points at last year's calendar is a confident wrong direction. The August 2026 update of the proposal did not change this duty. The list means what it says, or it should not be up.

## Common mistakes

The first mistake is expecting Google to fetch it. The guide says Google does not use llms.txt for generative features in search. Publishing one and waiting for AI Overviews is a plan the guide already declined. Fix the page Google can index.

The second mistake is a generated dump. Every tag, every attachment, every draft. The proposal is a curated list. A dump hides the staff-picks page inside noise, which is the opposite of pointing a model at your best work. It also rots, because nobody will curate a thousand automatic lines. We would rather Cole maintain a list he can read aloud.

The third mistake is treating the Ahrefs shares as a personal failure or a personal trophy. 28% of those 137,210 domains had a file. About 38,000 valid files. 97% with zero requests in May 2026. You are not behind because you lack one, and you are not ahead because you have one that nobody requested. The study describes a crawl of files. It does not describe your customers.

The fourth mistake is reading bot traffic as adoption. 96% of the requests that arrived were bots. 12% were audit or scanner tools. 19.5% were named AI tools. None of those sentences say a reader found the shop. Report them as machine requests, or do not report them.

The fifth mistake is letting the file contradict the floor. The events page says Thursday. The file's blurb says Wednesday, copied from an old night. Whichever surface gets quoted, you look careless. One source of truth, the live page, and the file follows it.

The sixth mistake is doing the file instead of the page, because the file is smaller. A map to a vague homepage is still a vague homepage. The pages have to be worth citing whether or not the file is ever requested. That is the whole practical reading of a study where almost all the valid files sat untouched for the month they measured.

## What we'd do

We would publish a short file only after the pages are true, and we would not tell Ade it will bring her readers. Our opinion is that the proposal is a reasonable courtesy and a bad priority. September 2024 was when the idea was written down. August 2026 is when the page was updated. June 2026 is when a large measurement, 137,210 domains, found that 97% of valid files got zero requests and that 96% of the requests which did show up were bots. Courtesy is allowed to be quiet. Strategy is not allowed to ignore a quiet result.

Google has said it does not use the file. So we would spend Cole's evening on the staff-picks page, the ordering explanation, and an events page that survives a cancellation. Then we would add a list of those URLs if Ade likes being able to see, in one place, what the shop claims. We would keep our own file for that same reason, and we would never wave it as proof of traffic. A file is a pointer. The page is the thing a person came for. If you only have time for one, choose the page, and let the pointer wait until the page would survive being read without it.
