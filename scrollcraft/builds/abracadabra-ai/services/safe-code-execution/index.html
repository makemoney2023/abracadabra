A finished task is more than a reply

Some jobs are not a sentence. They are a calculation, a file checked against a rule, a draft built from rows you already have. A person copies the numbers out, runs them, and pastes the result back. The assistant could take that step. Giving it a whole computer is how a small task becomes an incident.

The useful version is narrow. The assistant may run the task you named, on the files you named, for a length of time you named. When it reaches that bound, it stops and tells a person. This page is that sandbox. The assistant page is the system that talks to your customer.

What you get

  • A task, not a blank console

    The job is specific: this calculation, this check, this draft. A request to do something else is refused.

  • Bounds you can point at

    Time, memory, and which files it may read or write are set before it runs. Those bounds are part of the plan.

  • A result you can read

    The output comes back to the assistant with what it used. You can run it again or throw it out.

  • A stop that is loud

    If the task exceeds the bound or asks for something off the list, it stops. The log says why. It does not retry its way around the fence.

Use cases

  • A calculation from rows you trust

    The assistant takes numbers already in the file and returns the total the rule describes. It does not reach for a different spreadsheet because the first one was inconvenient.

  • A check before something is sent

    A file is tested against the rule you wrote: required fields, a total that matches, a name that exists. Failures go to a person with the reason.

  • A draft from a template

    The task fills a template already on the list. It does not invent a new template, and it does not send the result. Sending stays a separate step.

How it works

You tell us the job. We plan it, build it, and keep it running.

  1. Plan

    You tell us the job, the rules, and the moments that still belong to a person. We write that down before anything is built, so the build has one picture of how you work.

  2. Build

    We build it on Cloudflare and connect the records you already keep, so the work continues in the tools you already use.

  3. Review

    We test it on last week's real work. A customer-facing step goes live only after that test.

  4. Launch and run

    It goes live with the first runs watched. You can change the rules, and you leave with the system.

FAQ

Is this a server to rent and forget?

No. It is a task the assistant runs, inside a sandbox, on Cloudflare. An open machine and a password are not part of the delivery.

Can it install whatever package it wants?

No. Dependencies are the ones on the list. A request to fetch something new stops.

Can it reach production records?

Only the read or write you named. A wide credential is a failed plan. The task should be unable to see a table rather than able to see all of them.

What if the model writes bad code?

The task still runs inside the sandbox, and the result is not sent until the review you set. A crash is a log line, not a change to the record.

Do you have to read the code?

You read the task in plain language: what it may open, what it may write, and when it must stop. We maintain the code.

Can this be bought without an assistant?

The page stays up so the sandbox is easy to find. The thing that ships is the assistant with this capability turned on for the tasks on the list. Without an assistant, there is nothing to fence.
