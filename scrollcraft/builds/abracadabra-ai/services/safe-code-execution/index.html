A chat reply is not a finished task

Some jobs are not a sentence. They are a calculation, a file checked against a rule, a draft built from rows you already have. A person copies the numbers out, runs them, and pastes the result back. The assistant could do that step. Giving it a whole computer is how a small task becomes an incident.

The useful version is narrow. The assistant may run the task you named, on the files you named, for a length of time you named. When it hits the fence, it stops and tells a person. The page you are reading is that fence. The assistant page is the thing that talks to the customer or the team.

What changes

  • A task, not a blank console

    You approve the job: this calculation, this check, this draft. A request to do something else is refused.

  • A limit you can point at

    Time, memory, and which files it may read or write are set before it runs. The limit is part of the brief, not a hope.

  • A result a person can read

    The output comes back to the assistant with what it used. A person can rerun it or throw it out.

  • A stop that is loud

    If the task exceeds the limit or asks for something off the list, it stops. The log says why. It does not retry its way around the fence.

Three places it shows up

  • A calculation from rows you trust

    The assistant takes numbers already in the file and returns the total the rule describes. It does not pull a different spreadsheet because the first one was inconvenient.

  • A check before something is sent

    A file is tested against the rule you wrote: required fields, a total that matches, a name that exists. Failures go to a person with the reason.

  • A draft from a template

    The task fills a template you approved. It does not invent a new template, and it does not send the result. Sending stays a separate approval.

How it gets built

The order is the same on every service. The job is what changes.

  1. Brief

    You tell us the job, the rules, and the moment a person has to say yes. We write that list before anyone builds. A step that is not on the list does not ship.

  2. Build

    We build it on Cloudflare and connect it to the records you already keep. The new system should not be a second place to type the same fact.

  3. People approve

    Your team runs last week's real work through it and marks what may go live. We do not put a customer-facing step in front of people on our say-so alone.

  4. Launch and run

    It goes live. We watch the first runs with you, fix what the real work shows, and leave the rules where your team can change them.

Questions

Is this a server we rent and forget?

No. It is a task the assistant runs, with a limit, on Cloudflare. You do not get an open machine and a password.

Can it install whatever package it wants?

No. Dependencies are the ones you approved. A request to fetch something new stops.

Can it reach our production records?

Only the read or write you named. A wide credential is a failed brief. We would rather the task be unable to see a table than able to see all of them.

What if the model writes bad code?

The task still runs inside the limit, and the result is not sent until the approval you set. A crash is a log line, not a change to the record.

Do we have to read code?

You have to read the task in plain language: what it may open, what it may write, and when it must stop. The code is ours to maintain. The permission is yours.

Can we buy this without an assistant?

The page stays up so the limit is easy to find. The thing we ship is the assistant with this capability turned on for the tasks you listed. If there is no assistant, there is nothing to fence.
