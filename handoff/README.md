# Handoff

Handoff is a private locker. An operator invites someone, they drop files for one workspace, and a scan worker marks each file clean, rejected, or held. Handoff is not part of any client's product. It does not import into a client's app, and it does not share a database, cookie, or package with the operations site.

## One region

Keep the app, the database, and the file bucket in one region. Do not replicate a workspace's files to a second region.

## Local setup

```bash
cd handoff
npm install
npm test
npm run dev
```

`npm test` runs the unit suite, including workspace isolation. Those tests apply `migrations/0001_handoff.sql` through `migrations/0009_conversations.sql` to Node's built-in SQLite. `npm run test:db` runs the same isolation file. No Docker or hosted database is required.

Copy `.env.example` to `.env.local` for the Next app and to `.dev.vars` for Wrangler. Leave secrets out of git. Local runs that are not inside a Worker store records in `.data/handoff.db`.

## Deploy checklist

Cron changes ship with worker `handoff` and `wrangler.jsonc` (`npm run deploy`). They do not ship with `wrangler.hq.jsonc`. That file deploys `handoff-hq` and has no crons, so a settle or wake change that is deployed only there never runs. Deploy `handoff-hq` when HQ chat tools change, `handoff-agent` when notices or skill reads change, and the swarm worker when a run's model or callback changes. `handoff` and `handoff-hq` both bind the `handoff-skills` bucket as `SKILLS`. `AGENT_WAKE_SECRET` and `AGENT_URL` must be set on `handoff` or a finished stage cannot post into HQ chat. `SWARM_RUN_SECRET` is set on `handoff-hq` and the swarm. The swarm posts `POST /api/swarm-settled` to `https://hq.abra-ca-dabra.app`. The one-minute cron on worker `handoff` remains the fallback. Copy `SWARM_RUN_SECRET` onto worker `handoff` as well if that host should accept the callback.

## Staff screens

Moving between staff screens shows skeleton bars while the next page loads. The bars sit on the theme border, so the wait does not flash an empty light table.

## Writing style

All text people see (screens, emails, error messages) is written in short, plain sentences at about a grade 5 reading level. Say "space" (not workspace or locker), "storage limit" (not quota), "admin" (not super-admin) and "delete" (not purge). Code names, routes, status values and database fields keep their technical names.

## Finished work

Staff add finished work on a project page, then open it at `/deliverables/[id]`. Send to the client publishes the current round. ## Social publishing

Each client has a Social tab (`/clients/[id]?tab=social`) on the staff host. It lists the client's connected social accounts and the posts sent for that client. Connect opens the network's own sign-in through [Zernio](https://zernio.com/llms.txt) and comes back to the tab. We never see the client's password. Each client is one Zernio profile whose `externalId` is the organization id (`social_profiles`). Accounts are cached in `social_accounts`; opening the tab reads them again from Zernio and refreshes posts that should have gone out.

A finished-work page has Post to social. Staff tick pieces (All pieces selects every one) and accounts (All accounts), then Schedule, Post now, or Save as drafts in Zernio. A schedule starts at the picked time in the picked time zone, and each next piece waits the picked gap (same time, 1 hour, 3 hours, 1 day, 2 days, 1 week). Post as is Match each piece by default: a story piece goes as a story, two or more files as a carousel, a video as a reel (a YouTube Short on YouTube), and anything else as a feed post. Staff can force Feed post, Carousel, Reel, Story, or YouTube Short. An account that cannot take that post type is skipped and named (for example, YouTube without a video, or a story on LinkedIn). TikTok gets the post as a draft in the creator's TikTok inbox. Schedule and Post now need the client to have approved the piece; drafts do not. An account that already has a piece is skipped, so pressing Schedule twice does not post twice.

The caption is the piece's copy, the title is the piece's title, and the media are the piece's R2 files (slides in order after the main file, otherwise the main or square file; the poster is the video cover). HQ copies them to Zernio with a presigned upload and creates one Zernio post for all the picked accounts. Each send is a `social_posts` row written before the call, so a failure stays on the Social tab with Zernio's reason. `ZERNIO_API_KEY` is a secret on `handoff-hq`; without it the tab and the card say Zernio is not set up. The plan, including analytics and the inbox, is [docs/superpowers/specs/2026-10-21-social-publishing-design.md](../docs/superpowers/specs/2026-10-21-social-publishing-design.md).

Each scheduled post sits on the Social tab's Calendar, grouped by day, with Move (new time and time zone, sent to Zernio) and Cancel (taken off Zernio; it stays listed as cancelled). Posted items show their public links. Each piece has Text per network on its finished-work page: a caption per network (empty uses the piece's caption), a first comment (Instagram, Facebook, LinkedIn, YouTube, Threads, X), and YouTube tags, all kept with the piece and used by every later send, including select-all. Large videos stream from R2 into Zernio's upload instead of loading into Worker memory.

Auto-schedule on the Social tab picks accounts, weekdays, times (24-hour) and a time zone. When it is on and the client approves a piece (or a whole round) in their space, each approved piece that has not gone to those accounts yet is scheduled into the next free slot, as its own post type, recorded as a system post. A slot that already holds a scheduled post for that client is skipped.

Zernio reports post and account events to `POST /api/zernio/webhook` on the staff host. The body is checked against `X-Zernio-Signature` (lowercase hex HMAC-SHA256 of the raw body with `ZERNIO_WEBHOOK_SECRET`); an empty secret refuses every delivery. Each event id is handled once (`social_webhook_events`). A post event sets the status, per-network errors, and public links; `account.disconnected` marks the account for sign-in again; `account.connected` re-reads that client's accounts. `npm run zernio:webhook` registers the webhook (needs `ZERNIO_API_KEY` and `ZERNIO_WEBHOOK_SECRET`). The one-minute cron on worker `handoff` also re-reads posts due in the last six hours that still say sending or scheduled, when `ZERNIO_API_KEY` is set on that worker.

The client's owner (and assigned staff) has Social in their space (`/w/[slug]/social`): connect or disconnect the client's accounts with the same sign-in, and see what is coming up. HQ chat has `list_social_accounts`, `list_social_posts`, and `schedule_social` (approval card; same rules as the form: only approved pieces schedule or post now; empty lists mean every piece and every social account).

Assigned agents read social state at `/api/agent-social` (overview, pieces, accounts, posts, cadence, attention, and plans). Writes on those routes, and the HQ `save_social_variant` tool, stay off unless `SOCIAL_AGENT_ACTIONS` is `1`, `true`, or `on`. `schedule_social` still sends directly through the existing approval card: an empty piece list is every piece, and an empty account list is every connected social account. New HQ tools prepare an exact plan (`prepare_social_publish`, plus move, cancel, retry, cadence, connect, and disconnect). `execute_social_plan` uses the same approval card. An empty list on a prepare is not every piece. Staff Post to social still sends with All pieces and All accounts. The old review composer is not on that page. The operations list names Move, Cancel, and Retry as a plan review; the calendar Move and Cancel forms still send directly. When publishing cadence is on, the client's Approve control names the time zone, days, and times. New connect buttons are the social networks only. Accounts already connected, including blogs, stay listed. Blog publishing, Pinterest-specific workflows, and analytics stay out of this pass. See the [agent-managed social publishing design](../docs/superpowers/specs/2026-10-21-agent-managed-social-publishing-design.md) and [implementation plan](../docs/superpowers/plans/2026-10-21-agent-managed-social-publishing.md).

### Client agent work filing (prototype)

Client agents (Grok Bot teammates and hires) each have their own Bearer token (`caw_…`, stored as SHA-256 only). Client Services issues it and sets assignments with `POST /api/client-services/agents` (Bearer `CLIENT_SERVICES_TOKEN`): `{ agent_id, label?, client: { organization_id | domain | space_slug }, space_id?, project_id?, role?: lead|hire, rotate?, end? }`. A client can have many agents, and an agent can serve many clients. The token comes back once, on create or `rotate: true`.

`POST /api/agent-work` files anything finished (deliverables, notes, plans, logs): `{ external_id, title, kind?, summary?, client_summary?, content?, attachments?: [{ name, body }], links?: [{ label, url }], client?, project_id?, task_id?, keep_task_open?, handoff?: { to, note? }, finished_at?, supersedes?, work_request_id?, thread_id?, deliverable_kind? }`. Size limit below; anything bigger goes as links. `external_id` makes repeats return the first result. The client must be one of the agent's live assignments. With several, `client`, `task_id`, or `project_id` picks one. A space slug, project, task, or the assignment's space picks the space. Anything else is `unfiled` (`agent_not_assigned`, `ambiguous_client`, `client_mismatch`, `ambiguous_space`, `no_space`, `project_not_open`, `task_not_in_client`, `space_rejected`), and a matching domain is only kept as a suggestion. Filed work lands in its `folder` (below; default `Finished work/<YYYY-MM-DD> <title>/summary.md` plus attachments) in a batch labelled `From <agent>`, goes through the usual scan, is **held** until Client Services approves it (below), sends `task_id` to Waiting on Client Services instead of closing it (unless `keep_task_open`), logs `client_agent.work_filed` (and `client_agent.handoff` when `handoff.to` names another agent on the same client), and shows in the Client Services updates feed.

The agent APIs (`/api/agent-work`, `/api/agent-media`, `/api/agent-board`, `/api/agent-projects`, `/api/agent-contacts`, `/api/agent-skills`, `/api/agent-skill-library`, `/api/client-services/*`) are served on **hq.abra-ca-dabra.app only**. `agent.abra-ca-dabra.app` is the separate agent worker and does not serve them.

**Size limit.** One filing carries up to `AGENT_WORK_MAX_MB` MB of files (Worker var in `wrangler.hq.jsonc`, default **10**, clamped to 1–50), counted after base64 decoding: every attachment plus `content`. The raw JSON may be about 4/3 of that plus 1 MB (about 14.3 MB at the default), because base64 grows data by a third. Over either limit the answer is **413** `{ error, code: "too_big", limit_mb }`, checked from `content-length` before the body is read and again on the decoded bytes; nothing is stored. More than 50 attachments is a 400 (they used to be cut to 20 silently). Split big work into several filings on the same card (they join one deliverable version) or send links. Other limits on the path: Cloudflare Workers take 100 MB request bodies on Free/Pro (200 MB Business, 500 MB Enterprise) and 128 MB of memory, which is why 50 is the ceiling; file bytes go to R2, never D1; a payload that waits as unfiled is kept in R2 (`agent_work_items.payload_key`) once it passes 256 KB, so no D1 row comes near D1's 2 MB row limit; per-file and per-batch caps (`policy/limits.ts`) are 2 GB a file, 10 GB and 2,000 files a batch, and the space's quota; the virus scan (`worker/clamd.conf`) scans up to 2 GB a file.

**Media.** `GET /api/agent-media/models` lists the stills and clips this agent can ask HQ to run. Each row has `id`, `kind` (`image` or `video`), `reference_image` (`none`, `optional`, or `required`), `fits` (one or more of `text-to-image`, `edit`, `text-to-video`, `image-to-video`, `upscale`, `background`), and a short `note`. `?fits=text-to-video` returns only models for that job. The agent picks `model`. HQ does not choose one. `POST /api/agent-media` takes `{ external_id, model, prompt, task_id?, client?, image_media_id?, aspect_ratio?, duration_seconds? }`. `prompt` is required except for `upscale` and `background`, which need `image_media_id` and ignore a prompt. A prompt is at most 2,000 characters. A clip's `duration_seconds` is 4, 6, or 8 (6 when omitted), unless that model's `note` names a shorter set. `task_id`, when sent, must be an open card on a client this agent is assigned to. Without it, one assignment is the client, and several assignments need `client` (organization id or domain) or the answer is 400 `Name the client.` The file is stored for that client. It is not a social post and it does not create a social piece. HQ calls the Workers AI binding and stores the bytes in R2. The answer is `{ state: "ready", media_id, kind, content_type, bytes, name }` or `{ state: "running", media_id, job_id }` while a clip renders. Poll `GET /api/agent-media/:media_id`. The answer never includes a provider URL or the file bytes. A repeat `external_id` returns the first result. Pass ready ids as `media_ids` on `POST /api/agent-work` (up to 12) when the work should be filed. That filing is ordinary held work. Social posting stays a separate later choice. Those files are copied into the filing. A still is capped at 8 MB and a clip at 20 MB. A running id is 409. An id from another agent is 403.

**Attachments.** `attachments[].body` (or `content`, same meaning) is text, or a base64 data URL: `data:image/png|jpeg|webp|gif;base64,…` or `data:application/pdf;base64,…` (the bytes must really be a PNG/JPEG/WebP/GIF or start with `%PDF`). Anything else in a data URL, including `video/mp4`, is stored as text. Send a clip through `media_ids` instead. A text body named `.html`, `.htm`, `.csv`, `.txt`, `.xml`, `.css`, `.md`, `.json` (valid JSON) or `.svg` keeps that extension; other text becomes `.md`. HTML and SVG are download-only: they never render in the preview. Files land in the filing's folder under their own names.

**What the client reads.** On Finished work (and when a client opens a filing's `summary.md`), an agent filing shows as a card: the title, **Delivered** with the date and time in Toronto time (from `finished_at`, else when HQ received it), a short summary, the links, and "Show details" with `content` rendered as markdown (no raw HTML, outside images or unsafe links; `` `schema-1.png` `` links to that file on the page). The `- Kind / Agent / Finished / Task / Handed to / Ref` lines, `handoff.note` and the `## Files` list never reach client members (the files are listed under the card). Staff on the space also get "Details for staff" with those lines and the stored page. Send **`client_summary`** (up to 2,000 characters, plain words for the client: what is ready and what they should do; no ids, card numbers or agent names) to control the first thing the client reads; `summary` stays your note for Client Services and moves into the details. Without `client_summary`, the client reads `summary`, so keep it client-safe. No migration: it is a `## For the client` section of the stored summary page.

**Folders (migration 0033).** `folder` is a path in the space like `Social/Facebook`, `Blog` or `Brand/LinkedIn` (up to 6 levels; `/` or `\` separate levels; `.`/`..` and non-text are `400`). Without it, work goes to `Finished work/<YYYY-MM-DD> <title>/` (UTC date). The summary is `summary.md` in the default folder, or `<title> - summary.md` in a named one. Attachments keep their names (`schema-1.png`); a name already used in the folder (by a batch that isn't hidden) gets ` (2)`, except names of filings this one `supersedes`, which the replacement keeps. The folder is stored on the filing (`agent_work_items.folder`) and returned as `folder`. Filings from before keep their `agent/work/<run>/` paths, which the file list shows under `Finished work/<run>`. The space file list is a folder tree (closed by default, with recursive counts and Open all / Close all), each file has a type badge (Image · PNG, PDF, Doc · MD, HTML, Spreadsheet · CSV, Zip…) and images get a lazy thumbnail from the preview route. Held files show their hold note to staff only, as before.

**Built work (migration 0035).** `built_work` on `POST /api/agent-work` files websites and other things we built as cards in the client space: one object or a list of up to 12, each `{ title, live_url?, preview_url?, repo_url?, description?, status?, screenshot? }`. `live_url` or `preview_url` is required; every URL must be https. `status` is `live` (default with a live URL), `preview` (default without one), `in_progress` or `archived`. `screenshot` is the name of a PNG/JPEG/WebP attachment in the same filing, or a `data:image/png|jpeg|webp;base64,…` URL that becomes an attachment `<title>-screenshot.<ext>`; either way it is a file of the filing's batch in R2 and counts toward the size limit. A filing may be `built_work` alone. Rows go to table `built_work` (one per item, tied to the filing and its batch, with the screenshot's file id). The deliverable kind defaults to `website`. Visibility is the batch's: held until Client Services approves the card, hidden once a `supersedes` replacement is approved or the filing is withdrawn. The client space home (`/w/<slug>`) shows them at the top as "What we built" cards (screenshot, status pill, title, host, description, Visit site / Preview / Code); staff on the space also see held and retired cards with the hold note and the agent, and the HQ client **Agent work** tab lists them all as **Built work**. The screenshot is served by the existing `/api/files/<id>/preview` route, with the same hold check. The response adds `built_work` (count) and `GET /api/agent-work` items carry `built_work`. The summary page gets a `## Built work` section that the client summary card skips.

**Already delivered (catalog).** A filing with `already_delivered: true`, or `kind: "catalog"`, is work that was finished before it was filed (most built-work showcase entries). It is held and reviewed like any filing, but Client Services' approval publishes its deliverable as `approved` (delivered; its pending items approved) instead of `in_review`, and posts no `client_work.update_ready` suggested update and no "is ready" email, in either update mode. Stored as `agent_work_items.already_delivered`. If a card's approval releases a mix, the normal in_review path wins. For a deliverable that already went out as `in_review`, Client Services can call `POST /api/client-services/deliverables/<id>` `{ "action": "mark_delivered", "reason"? }` (Bearer `CLIENT_SERVICES_TOKEN`): it sets `approved`, approves the published version's pending items and logs `deliverable_marked_delivered`, with no notice. 409 unless the deliverable is `in_review` with a published version and no newer held filing; approved already returns `already: true`.

`HANDOFF_SKIP_MIGRATIONS` (Worker var, comma-separated migration file names) holds those steps back. Preview uploads share the production D1, so a preview of a branch with a new migration sets it (for example `--var HANDOFF_SKIP_MIGRATIONS:0033_agent_work_folder.sql`) to keep the live schema unchanged until the release. Never set it on a deploy.

**Hold until approved (migration 0032).** Every agent batch is stored with `batches.held_at` set. Staff on the space, Client Services and agents see it; client members do not see it in the folder, file pages, previews, downloads, signed links, exports, knowledge search or the MCP space key, and no client mail goes out. Batches filed before 0032 (`held_at` NULL) stay visible as before; no data is rewritten. Each filing with a `task_id` creates the card's deliverable (`tasks.deliverable_id`) or adds to it: filings join the open version, and a new version starts after the last one was published, after a send-back, or when the filing supersedes another. The card goes to Waiting on Client Services; a Done card is reopened into review (`task_reopened: true`). The response adds `held: true`, `deliverable_id`, `deliverable_version`, `awaiting_review`, `task_reopened`, `work_request_id` and `superseded`. A filing with no card stays held and is listed in `loose_filings` on `GET /api/client-services/reviews` (and `GET /api/client-services/filings?loose=1`): file it again on a card with `supersedes`, or withdraw it.

Client Services **approve** (`POST /api/client-services/reviews/:taskId` `{ action: "approve" }`, or approving the whole deliverable in the space review) releases the card's held batches, hides what they superseded, publishes the deliverable at the newest version and logs `deliverable_published`. The client notice follows the client's **Client updates on approved work** setting (`organizations.client_update_mode`, Settings tab, staff only): `draft` (default) emails nothing and posts `client_work.update_ready` to the Client Services updates feed with `suggested_update: { to, subject, body, thread_id, source_message_id, space_slug }` for Client Services to draft from magic@; `auto` queues the usual `deliverable.published` mail once per version. **Send back** keeps everything held.

**Supersede and withdraw.** `supersedes: "<work item id>"` or an array (up to 20) names earlier filings of the same client this one replaces (the same agent's, or any on the client for its lead; not withdrawn, not already superseded). A held old filing is hidden at once; a released one, or one filed before the hold, leaves the client's view when the new one is approved. `POST /api/agent-work/:id` `{ action: "withdraw", reason? }` withdraws an agent's own held filing (the lead: any on its client): the batch is discarded and its deliverable items dropped; once the client can see it, it is 409 (file a correction with `supersedes`). Client Services can withdraw any filing, released or filed before the hold, with `POST /api/client-services/filings/:id` `{ action: "withdraw", reason? }`: its batch is hidden from the client and kept for staff. `GET /api/client-services/filings?client=&task_id=&loose=1&limit=` lists filings with `visibility` (`held`, `released`, `superseded`, `withdrawn`, `published` = filed before the hold).

**Request links.** Client Services records the request it hands to a lead with `POST /api/client-services/requests` `{ client, subject, thread_id, source_message_id?, client_email?, brief?, project_id? }` (201 new, 200 when that thread already has one; logs `client_work.handoff`) and passes the returned `work_request_id` on. Card create (`POST /api/agent-board/tasks`) and filings accept `work_request_id` or `thread_id`; a `thread_id` with no request makes one. The card, the filings, the review and `suggested_update` then point at the original email thread.

Agents read context back with `GET /api/agent-work?client=&since=&kind=&handed_to_me=1` (filed work for their current clients, from any agent) and `GET /api/agent-work/:id` (with the summary markdown). Skills: Client Services grants path prefixes in `handoff-skills` to an agent or a client with `POST /api/client-services/skill-grants` `{ agent_id? , client?, prefixes[], revoke? }`. Agents list them with `GET /api/agent-skills?q=` and read one with `GET /api/agent-skills/<path>/SKILL.md` (ETag is a content hash). HQ reads the bucket through its `SKILLS` binding; no bucket credential or signed URL is handed out.

Skill library and card packs: any registered agent token can browse the full library, granted or not. `GET /api/agent-skill-library` lists every pack (`prefix`, `name`, `count`, `description`) plus `skill_count` and `library_version`; `?q=` (words) and `?pack=<prefix>` also return matching `skills`. `GET /api/agent-skill-library/<path>/SKILL.md` reads any skill (`org/` is 404). An agent attaches packs to an open card of a client it is on (lead or hire), at assignment or any time before Done, review included: `POST /api/agent-board/tasks/:id` `{ action: "attach_skills", prefixes: [...] }`, and `{ action: "detach_skills", prefixes: [...] }` takes them off. A prefix is a pack (`community/marketingskills/`) or one `…/SKILL.md`, and must name at least one library skill. Repeats are no-ops. Errors: 400 empty `prefixes`, 403 a card of a client the agent is not on, 404 a missing card or an unknown pack (nothing is written), 409 a done card. Each change logs `client_agent.board` ("<agent> attached <packs> to "<title>".") and shows as chips on the card in the staff board and the client page. Attached packs live in `task_skill_packs` (migration 0029) and count in `GET /api/agent-skills` and the read route on top of Client Services grants until the card is done; the list returns `attached: [{ task_id, prefix }]`, and `?task_id=` narrows to that card's packs plus grants. Lead dispatches carry `skills: { attached, library, attach }`.

Skill usage (migration 0034, table `skill_events`): every list, search, read, attach, detach, and cite is logged with the agent (or staff member), the client, and the card, after the response (`waitUntil`), and a failed log write never fails the request. Agents tie a lookup or read to a card with `?task_id=` on `/api/agent-skill-library` and `/api/agent-skills` (it changes nothing in the answer). Staff chat's `search_skills` and `read_skill` post to `POST /api/hq-chat/skill-events` with the chat token. A filing can say which skills it followed: `skills_used: ["community/marketingskills/copywriting/SKILL.md", …]` on `POST /api/agent-work` (up to 30 SKILL.md paths; `org/` and non-skill paths are `400`). Paths that are not in the published index are dropped and listed back as `skills_unknown`; the rest are stored in `agent_work_items.skills_used_json`, echoed as `skills_used`, and logged as `cite` on the card. The Agents page shows "N packs · M skills · published <date>" (from `skills/manifest.json`), each pack's count and description in the grant drawer, "Suggested for <client>" packs from the client's name, domain, industry, and notes (nothing is granted until staff press Grant), and a Skill usage table per pack and per skill for 7, 30, or 90 days: reads, cites, attaches, cards, approved, sent back (from `client_services.task_review` and `staff.task_review` on those cards; approved = latest decision approve), approval rate, last used, plus the packs never used since tracking started.

Publishing the library is manual: `cd handoff && npm run publish:skills` (needs `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_ENDPOINT` in `handoff/.env.local`). It uploads every SKILL.md, then `skills/index.json`, then `skills/manifest.json` (`published_at`, `git_sha`, `file_count`, `skill_count`, `pack_count`, `fallback_count`). A SKILL.md without YAML front matter is still indexed: its name is the folder name and its description is the `description:` line or the first paragraph. `npm run publish:skills:dry` prints the manifest without uploading or reading credentials.

Board updates: agents change tasks on their current clients' boards with the same token. `GET /api/agent-board?client=&project_id=` lists tasks. `POST /api/agent-board/tasks/:id` takes one of `{ action: "start" }` (in progress), `{ action: "pause" }`, `{ action: "block", reason }`, `{ action: "review", note? }`, `{ action: "move", to: todo|doing|review|done }`, `{ action: "note", body }`, or `{ action: "attach_skills" | "detach_skills", prefixes }` (above). The board has four columns: To do, Doing, Waiting on Client Services, and Done. The old stage names still work as move targets: `describe` is `todo`, and `engineer`, `build`, and `run` are `doing`. A move to Doing stores stage `build`; with `AGENT_MODE=agents` it hands the task to the card's agent assignee, else the lead agent. A card waiting on Client Services can't be started, paused, moved, or finished by an agent. Client Services approves it or sends it back. `POST /api/agent-board/tasks` `{ title, note?, stage?: todo|doing, client?, project_id?, assignee?, work_request_id?, thread_id? }` creates a task (the project defaults to the assignment's, then the client's only open project). `assignee` is an agent id on the same client (400 otherwise); a lead may name anyone on the client, a hire's cards default to itself and it can't name another agent (403). Every change logs `client_agent.board` on the timeline, which the Client Services updates feed carries. There are no deletes. Moves to Doing are refused while `AGENT_MODE` is legacy, since they would start a Cursor or swarm run.

Projects and card owners (migration 0031): a client can have several projects, each with its own space. `GET /api/agent-projects?client=&closed=1` lists the projects of the agent's clients (`id, name, status, open, description, space: { id, slug }, open_cards`), open first. The client's **lead** opens one with `POST /api/agent-projects` `{ name, description?, client? }`: it gets its own new space (or the client's one unlinked space), a name the client already has (any case) returns that project with `created: false`, hires get 403, and past 20 open projects it is 409. Each card has an optional agent owner, `tasks.assignee_agent_id` (null means the lead). The lead reassigns with `POST /api/agent-board/tasks/:id` `{ action: "assign", to: "<agent id>" | null }` (hires 403; an agent not on the card's client 400); a card already in Doing is handed to the new owner right away. `GET /api/agent-board?mine=1` lists only the cards the agent owns, and every card carries `assignee_agent_id`. Dispatches (a move to Doing, a Client Services send-back, a changes request) go to the owner while it is live and still on the client, else to the lead, with `assignee` and `fallback` in the entry. Staff see an agent badge on each card, an "Assign to agent" menu item, and an Agent filter on /work (`?agent=<id>` or `?agent=lead`). A staff-created project for a client that already works in spaces gets its own new space when no loose space is there to link.

Contacts for agents (migration 0036): contacts have an optional postal address (`address_line1`, `address_line2`, `city`, `region`, `postal_code`, `country`, all nullable), shown under each person on the HQ client Overview and set from the Add person form. `GET /api/agent-contacts?client=` lists the client's contacts for any agent assigned to it (`id, name, title, email, phone, primary, address: { line1, line2, city, region, postal_code, country, text }, opted_in, opted_out`; another client is 403). The client's **lead** adds one with `POST /api/agent-contacts` `{ client?, name, email?, phone?, title?, primary?, address? }` (201) and edits one with `PATCH /api/agent-contacts` `{ id, ...fields }` (only sent fields change; `""` or `null` clears; `primary: true` moves the main contact). Same validation as staff (`createContact`), and each change logs a contact activity with `actor_kind = 'agent'`. Hires get 403, a taken email 409, a contact on another client 404, and any `opted_in` / `opted_out` key 400. There is no delete.

`AGENT_MODE` (Worker var or env) is `legacy` when unset. With `agents`, no new swarm, scheduled workflow, Cursor build, or capped-build retry starts. A board move to build or run, or a client's ask for changes, is handed to the card's agent assignee (else the client's lead agent) as `client_agent.dispatch` (in the Client Services feed and in `GET /api/agent-work?dispatches=1` for the agent). Runs already going still settle.

`AGENT_WAKES` (secret or env on `handoff`) is `off` when unset. With `off`, HQ never wakes a per-client ClientAgent: the one-minute work wake, the scan-ready, lead-created, kickoff, review, board, and brief wakes are all skipped, and a skipped wake logs no `agent.wake_failed`, so the Today wake alert stays quiet. `no_lead_bot` wakes only clients with no live lead bot assignment. `all` restores the old behavior. The rest of the cron (scan filing, swarm settle and expiry, capped-build retries) keeps running. The weekly status wake (`0 8 * * 1`) is gone. Roll back with `wrangler secret put AGENT_WAKES` (value `all` or `no_lead_bot`) on `handoff`.

With `AGENT_MODE=agents`, the step engine does not move cards (client bots and Client Services do), and lead intake files the schema scan context only: no placeholder note and no "Qualify" task. The schema scan and `GET /api/leads/export` are unchanged.

The hq@ / magic@ mailbox on `handoff-agent` is log-only: each message posts `log_email` to `POST /api/client-messages`, which logs `email.received` ("New email from …") and puts it on the Client Services updates feed. It sends no reply. Bulk and vendor senders (List-Unsubscribe, List-Id, Precedence bulk/list/junk, Auto-Submitted, noreply-style addresses) never open a lead. A known contact lands on that client; an unknown person opens a lead as before. Set `MAILBOX_AUTO_REPLY=on` on `handoff-agent` to bring back the old auto-reply desk. MX and Email Routing are unchanged.

### Inbound replies (Readiness Check and the /start/ form)

Two inbound sources queue a reply from Sales Outbound with `routing_status = reply_needed` and `scored_at` set to the moment the submission arrived (that is what the export's `since` compares):

- A Readiness Check assessment (`POST /api/intake/assessment`) with an email. A new deal has `source = readiness_check`. An assessment that arrived without an email queues when the email fills in.
- A project inquiry from the marketing site's `/start/` form (`POST /api/intake/project-inquiry`, signed with `PROJECT_INQUIRY_SIGNING_SECRET`, same `x-intake-signature` / `x-intake-timestamp` HMAC). Required: `external_id` (dedup) and `email`; also `name`, `company`, `need`, `budget`, `timeline`, `message`, `page`, `submitted_at`. It matches the contact by email, then the org by email domain (freemail gets no domain), opens a `start_form` deal when the org has no open deal, and logs a `project_inquiry` activity with the form fields.

Rules (`queueReply` in `src/lib/lead-routing.ts`): only stages `new` and `contacted` (a deal at `call_booked` or `proposal` is left alone). A Readiness Check does not take a deal already in the BDR flow (`ready_for_outbound` or `enriched`); Sales Outbound already owns that conversation, usually because it sent the survey link. A project inquiry does take it, which also drops it out of the `enriched` export so the cold sequence stops. `replied` goes back to `reply_needed` on each new submission. Schema scoring (`applySchemaScore`) records `lead_score` on these deals but never changes `reply_needed` / `replied` or their `scored_at`, and a scoring failure never marks them `scoring_error`.

Sales Outbound pulls `GET /api/leads/export?status=reply_needed&since=ISO` (Bearer `LEAD_EXPORT_TOKEN`). Besides the usual fields, each lead has `reply_to` (`name`, `email` of whoever submitted most recently), `readiness` (from the assessment on that deal: `assessment_id`, `total_score`, `scores_json`, `answers`, `report_url`, `completed_at`) and `inquiry` (`external_id`, `company`, `need`, `budget`, `timeline`, `message`, `page`, `submitted_at`); either can be `null`. `source` says which form it came from. After the reply is sent, Sales Outbound posts `POST /api/intake/outreach` with that `deal_id`; it moves the deal from `reply_needed` to `replied` (and `new` to `contacted`), so the lead leaves the queue. `status=replied` lists the answered ones.

`POST /api/intake/deal-closed` (Sales Outbound, `OUTREACH_SIGNING_SECRET`): `external_id`, `deal_id` or `domain`, `closed_at`, optional `value_cents`, `products`, `notes`. Sets stage `won`, `closed_at`, org kind `client`, logs `deal.won`. Client Services pulls `GET /api/leads/export?status=won&since=ISO` (since matches closed_at).

Deal-closed also makes sure the won deal has a project (linked by `deal_id`) and a Space, using `planProjectSpace` (`src/lib/project-space.ts`), the same helper client work requests use.

`POST /api/intake/work-request` (Client Services, `CLIENT_SERVICES_SIGNING_SECRET`, same `x-intake-signature` / `x-intake-timestamp` HMAC): `source_message_id` (dedup), `client_email` and/or `client_domain`, `subject`, `brief` (a string, or `{ request, deliverables[], deadline }`), optional `attachments[]` (links), `project_id` (hint), `estimate_hours`, `size`. The queue matches the client by contact email, then org domain. A valid hint, the only open project, or one open project named in the subject gets the request; no open project creates a project and Space. It then adds a `describe` task with an `agent.task_brief`, wakes the HQ agent (`work`), and logs `client_work.kickoff`. Unknown client, ambiguous project, a bad hint, or over `AUTO_START_MAX_HOURS` (16) / `size: large` lands in `needs_approval` on the Work board, where staff approve (optionally picking org/project) or decline.

Client Services pulls `GET /api/client-services/updates?since=ISO|ms` (Bearer `CLIENT_SERVICES_TOKEN`): milestones for client orgs (`client_work.*`, tasks moved to done, deliverables published or ready, `deal.won`, and `email.received` from the mailbox) with project, summary, Space/Project/review links, and deliverables `needs_review`. Review uses the same token, which only opens these routes (read, comment, request changes, approve; no deploy or delete): `GET /api/client-services/spaces/:spaceId` and `POST /api/client-services/spaces/:spaceId/review` with `{ deliverable_id, decision: approve|changes|comment, body?, item_id? }`. Each decision is logged as `client_services.*` activity; `changes` wakes the agent. `GET /api/client-services/projects?client=&closed=1` (same token) lists clients' projects with their spaces, plus each client's live agents (`id, label, role`), so a handoff to the lead (or a work request's `project_id`) can name the right project. Without `client` it covers every client that has a live agent.
